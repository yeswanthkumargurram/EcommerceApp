# Scope Deviations — What This Sample Simplifies vs. the Full PRD/LLD, and Why

This repo is an **interview-learning sample**, not a production system. Every simplification below was a deliberate choice to keep the whole stack runnable on a laptop with `docker-compose` (MySQL, Kafka/Zookeeper, Redis, Elasticsearch) and no external accounts (no real Stripe/SES/Kong Cloud). Each row says what the "textbook"/production answer would be, so you can discuss the tradeoff in an interview even though the simpler version is what's actually running.

| Area | Production-grade approach (PRD/LLD target) | This sample | Why | More detail |
|---|---|---|---|---|
| Primary keys | `UUID` (globally unique, no coordination needed across DBs) | `BIGINT`/`Long` auto-increment | Matches the class diagram and every existing entity in the original codebase; `LLD.md`'s ER diagram using `UUID` while the class diagram used `Long` was an internal inconsistency, now fixed | `LLD.md` |
| Cart storage | MongoDB (flexible document store) | MySQL/H2 (relational) | Cart's shape never varies — no schema-flexibility benefit, one less datastore to run | [CART_SERVICE.md](CART_SERVICE.md) |
| API Gateway | Kong (dedicated gateway product, own admin API/DB) | Spring Cloud Gateway (`api-gateway` module) | Kong's config isn't meaningfully expressible as this repo's Java/Spring code; Spring Cloud Gateway teaches the same routing/rate-limiting concepts in a debuggable Spring Boot app | [API_GATEWAY.md](API_GATEWAY.md) |
| Payment gateway | Real processor (Stripe/Braintree/etc.), PCI-DSS scope, 3-D Secure, idempotency keys | `MockPaymentGateway` — deterministic simulator (declines on `.13` cents) | No sandbox credentials for a public sample; `PaymentGateway` interface is the swap point for a real adapter | [PAYMENT_SERVICE.md](PAYMENT_SERVICE.md) |
| Email/SMS | Amazon SES / SMS gateway | `LoggingEmailProvider` (logs + persists a `Notification` row) | Same reasoning as payment; `EmailProvider` is the swap point | [NOTIFICATION_SERVICE.md](NOTIFICATION_SERVICE.md) |
| Service discovery | Eureka/Consul + client-side or gateway-side load balancing | Hardcoded `localhost:PORT` / `services.product.base-url`-style config | Four extra services already added enough moving parts; discovery is an orthogonal concern that doesn't change the business-logic lessons here | `order-service`/`cart-service` `application.yml` |
| Order schema | `order_number`, tax/shipping split, `order_status_history` audit table, `order_delivery_addresses` table | Single `deliveryAddress` string column, status transitions inferred from the saga, no separate audit table | Keeps the entity simple while the saga/Kafka log itself is the de facto audit trail for this sample | `LLD.md` "Order Service Database" note |
| Payment schema | `payment_attempts.idempotency_key`, `payment_receipts` table, real gateway transaction IDs | `PaymentAttempt` records outcome/reason only, one attempt per order | No retries implemented yet, so idempotency keys/receipts have nothing to key off of | `LLD.md` "Payment Service Database" note |
| Product schema | `product_images`, `product_specifications`, many-to-many `product_categories` | Single `Product` entity with one `@ManyToOne Category` | Original codebase already modeled it this way; not worth a breaking schema change for this exercise | `LLD.md` "Product Service Database" note |
| Inventory | Separate "reserved" vs. "available" quantity (to protect against overselling during the pending window) | Single `quantity` column, decremented on reservation, incremented back on compensation | Simpler to reason about for learning the saga pattern; a real system would split these columns | [ORDER_SAGA_FLOW.md](ORDER_SAGA_FLOW.md) |
| Money type | `DECIMAL(19,4)` everywhere | `BigDecimal` for `Order.totalAmount`/`Payment.amount`, but `Product.price` is still a `double` (pre-existing) | Fixing `Product.price` would require a wider migration across `product-service`'s existing tests/data; flagged here rather than silently left unmentioned | [PAYMENT_SERVICE.md](PAYMENT_SERVICE.md) |
| Kafka delivery | Exactly-once / idempotent consumers (dedupe by event ID) | At-least-once, no dedup — a redelivered `OrderCreated` would double-reserve stock | Idempotent consumers are a real production requirement but a big enough topic to call out explicitly rather than half-implement | [ORDER_SAGA_FLOW.md](ORDER_SAGA_FLOW.md) |
| Search consistency | CDC (e.g. Debezium) streaming DB changes into Elasticsearch | Inline dual-write on create only (no update/delete sync) | Search is a secondary read path here, not the system of record; CDC is a bigger infra lift than this sample's scope | [ELASTICSEARCH_SEARCH.md](ELASTICSEARCH_SEARCH.md) |
| Gateway auth | Gateway validates/strips JWT, forwards trusted identity headers | Gateway only routes + rate-limits; every service still validates its own JWT | Avoids duplicating the JWT filter pattern into a 9th place; already well covered per-service | [API_GATEWAY.md](API_GATEWAY.md), [JWT-Interview-Prep.md](JWT-Interview-Prep.md) |

## How to use this file in an interview

If asked "why doesn't your cart use MongoDB like a typical e-commerce reference architecture?" — that's exactly the kind of question this table (and the linked per-concept docs) prepares you to answer with a reasoned tradeoff, not just "I didn't get to it."
